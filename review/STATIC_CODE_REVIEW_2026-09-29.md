**เวลาที่สร้างไฟล์:** 29 กันยายน 2569 เวลา 17:29:43 น. (Asia/Bangkok; 10:29:43 UTC, จากเวลา Birth ของไฟล์)  
**วิธีตรวจ:** อ่านโค้ด SQL สคริปต์ติดตั้ง เอกสาร และหลักฐานที่อยู่ใน repository เท่านั้น  
**ข้อจำกัด:** ไม่รันโปรแกรม ชุดทดสอบ ตัวติดตั้ง ฐานข้อมูล หรืออุปกรณ์เครือข่าย และไม่ได้ตรวจเครื่อง Raspberry Pi ที่ติดตั้งจริง  
**สถานะ:** รายงานประเมินจาก source ณ วันที่ระบุ ไม่ใช่ใบรับรองความปลอดภัยหรือข้อวินิจฉัยทางกฎหมาย

## 1. บทสรุปสำหรับผู้จัดทำโครงงาน

โครงงานมีองค์ประกอบหลักครบตามโจทย์: Admin Panel ออก voucher, Captive Portal เชื่อม openNDS, ตัวเก็บ Connection/DNS Log, ระบบค้นหา/ส่งออก/ตรวจความถูกต้องของ log และสคริปต์ตั้งค่า gateway บน Pi 4B หลักฐานใน `docs/hardware-test-log.md` แสดงว่าได้ทดลองกับอุปกรณ์จริงในห้องแล็บแล้วหลายกรณี โดยเฉพาะ captive portal, การตัดสิทธิ์ voucher, client isolation และการบล็อกการข้าม portal เมื่อเราเตอร์มี Access Control

อย่างไรก็ตาม **ยังมีเส้นทางที่ทำให้ DNS/Connection Log หายโดยไม่มีหลักฐานครบ**, วิธีค้นหา log อาจจับคู่ผู้ใช้ซ้ำหรือผิดคน, และสถานะ session อาจไม่ตรงกับการอนุญาตของ openNDS ข้อเหล่านี้กระทบวัตถุประสงค์เรื่องหลักฐานและความปลอดภัยโดยตรง ควรแก้ก่อนอ้างว่าระบบเก็บข้อมูลได้ครบอย่างต่อเนื่อง 90 วันขึ้นไป

ผลที่วัดไว้แล้วต้องรายงานตามจริง: เวลา login 3.90 วินาที ไม่ผ่านเกณฑ์ ≤3 วินาที; iOS/macOS, ARP spoof และ 20 client พร้อมกันยังไม่มีผลทดสอบตามขอบเขตล่าสุด (`PROJECT_PLAN.md:1090-1107`; `docs/hardware-test-log.md:375-405`)

### วิธีอ่านระดับความสำคัญ

- **วิกฤต:** ทำให้ข้อมูลหลักฐานสำคัญหายหรือการควบคุมสิทธิ์ผิดพลาดในเงื่อนไขใช้งานปกติ
- **สูง:** มีผลต่อความครบถ้วน ความถูกต้อง ความลับ หรือความต่อเนื่องของระบบ ควรแก้ก่อนส่ง
- **กลาง:** เป็นบั๊กที่มีเงื่อนไขเฉพาะหรือเป็นช่องว่างด้านการป้องกัน/เอกสาร ควรแก้หรือตีกรอบข้อจำกัดให้ชัด
- **ต่ำ:** ปรับปรุงคุณภาพและการใช้งาน ไม่ควรกลบปัญหาระดับสูง

“ยืนยันจากโค้ด” หมายถึงเส้นทางการทำงานตาม source นำไปสู่ผลที่ระบุได้โดยไม่ต้องเดาพฤติกรรมภายนอก แต่ **ยังไม่ใช่การยืนยันว่าเกิดขึ้นบน Pi เครื่องจริงแล้ว**; “ต้องพิสูจน์” หมายถึงผลลัพธ์ขึ้นกับ openNDS, nginx, OS หรืออุปกรณ์เครือข่าย

## 3. ข้อค้นพบจากโค้ด (แยกกรณีที่ต้องพิสูจน์ผลบนระบบจริง)

### R01 — ตัวอ่าน DNS ติดอยู่กับไฟล์เก่าหลัง logrotate [วิกฤต]

**หลักฐาน:** `app/logger/dns_collector.py:143-159` เปิด `dnsmasq.log` ครั้งเดียวด้วย `with open(...)` แล้วอ่านต่อจาก file descriptor เดิม; `install.sh:1782-1802` ตั้ง logrotate แบบย้ายไฟล์ไป `archive` สร้างไฟล์ใหม่ และ restart dnsmasq แต่ไม่มีการสั่งตัวอ่าน DNS ให้เปิดไฟล์ใหม่

**ลำดับเหตุการณ์:** ก่อนหมุนไฟล์ ตัวอ่านตามข้อมูลได้ → logrotate ย้าย inode เดิม → dnsmasq เริ่มเขียนลง inode ใหม่ → ตัวอ่านยังรอข้อมูลจาก inode เดิม → `dns_log` ไม่ได้รับ query ใหม่จนกว่า `cafe-logger` จะถูก restart การมีไฟล์ `dnsmasq.log` ที่เขียนได้ตามปกติอาจทำให้ปัญหานี้ไม่สะดุดตา

**ผลกระทบ:** หลักฐาน DNS ในฐานข้อมูลขาดหลังการหมุนไฟล์ตามรอบปกติ และการค้นย้อนหลังไม่พบข้อมูลทั้งที่ raw log มีอยู่

**แก้:** ตรวจ inode/path หรือออกแบบตัวตามไฟล์ให้เปิดใหม่เมื่อไฟล์ถูกแทนที่; หลังหมุนไฟล์ควรให้ collector รับรู้โดยไม่ทำข้อมูลค้างหาย ตรวจกรณีหมุนทั้งระหว่างไม่มีทราฟฟิกและระหว่างทราฟฟิกต่อเนื่อง

### R02 — DNS buffer ถูกล้างทั้งที่เขียนฐานข้อมูลล้มเหลว [วิกฤต]

**หลักฐาน:** `app/logger/dns_collector.py:149-168` ดัก exception จาก `insert_dns_rows()` แต่เรียก `buffer.clear()` ทั้งสองเส้นทาง รวมถึงกรณีเขียนล้มเหลว

**ตัวอย่าง:** MariaDB restart ระหว่างมี DNS rows 100 รายการ → `executemany()` ล้มเหลว → เขียน error ใน service log → ล้าง 100 รายการออกจาก RAM โดยไม่ได้เก็บกลับเข้าฐานข้อมูล

**ผลกระทบ:** ข้อมูลหายถาวรและไม่มีจำนวนแถวที่ทิ้งใน `audit_log`; ต่างจาก Connection collector ที่พยายามเก็บ buffer ไว้เมื่อ DB ล้ม (`app/logger/conn_collector.py:167-190`)

**แก้:** ล้าง buffer เฉพาะหลัง commit สำเร็จ; เก็บรายการไว้ retry พร้อมเพดาน RAM; หากเกินเพดานให้บันทึกจำนวนและช่วงเวลาของข้อมูลที่ทิ้งเป็น `log_gap` โดยพยายามส่งสัญญาณผ่าน journal เมื่อ DB ยังล่ม

### R03 — ตัวอ่าน log ตัวใดตาย แต่ service หลักยังดูเหมือนทำงาน [สูง]

**หลักฐาน:** `app/logger/run_all.py:40-51` เริ่ม conn/DNS collectors เป็น daemon threads แล้ว main thread รอสัญญาณอย่างเดียว; `install.sh:1519-1538` ตั้ง `cafe-logger.service` ให้ restart เฉพาะเมื่อ process ล้มเหลว

**ผลกระทบ:** หาก thread ตัวใด throw exception เช่นไฟล์อ่านไม่ได้หรือ subprocess หยุด ตัวหลักยังไม่ออกด้วยสถานะผิดพลาด systemd จึงไม่ restart อัตโนมัติ หน้า status ที่ดูเพียง service active อาจรายงานว่า logger ปกติ

**แก้:** เฝ้าการมีชีวิตและความคืบหน้าของ collector ทั้งสอง; ให้ process ออกด้วย nonzero เมื่อ collector สำคัญหยุด และมี alert ระบุชนิด log/เวลาล่าสุดที่เก็บได้

### R04 — Connection Log ถูกข้ามเมื่อหา MAC ไม่พบ [สูง]

**หลักฐาน:** `app/logger/conn_collector.py:151-159` เรียก `mac_cache.get(src_ip)` และ `continue` ทันทีเมื่อไม่พบ MAC; ตาราง `conn_log` บังคับ `mac NOT NULL` (`sql/001_schema.sql:83-98`)

**ผลกระทบ:** แถวที่เกิดขึ้นแล้วใน conntrack ไม่ถูกเก็บเลย โดยเฉพาะเมื่อ ARP entry หมดอายุ การบอกว่าเก็บ “ครบ 100%” จากการทดสอบ 500 connections จึงต้องจำกัดความว่าเป็นผลภายใต้เงื่อนไขแล็บครั้งนั้น

**แก้:** เก็บเหตุการณ์พร้อม IP และสถานะ “ยังระบุ MAC ไม่ได้” หรือทำ mapping จาก DHCP lease/ข้อมูล session ที่บันทึกขณะเชื่อมต่อ; นับและแจ้งแถวที่จับคู่ไม่ได้ อย่าให้หายเงียบ

### R05 — หน้าค้นหา log อาจแสดงหนึ่งเหตุการณ์เป็นหลายบุคคล [สูง]

**หลักฐาน:** `_MAPPING_JOIN` ใน `app/admin/app.py:524-535` จับ `device` ด้วย MAC แล้วเลือกทุก voucher ที่ `log.ts BETWEEN valid_from AND valid_until`; `device` unique แค่ `(voucher_id, mac)` (`sql/001_schema.sql:54-64`) และการออก voucher ใหม่ไม่ได้ยกเลิกใบเดิม (`app/admin/app.py:337-359`)

**กรณีที่เป็นไปได้:** ลูกค้าคน A ใช้อุปกรณ์ MAC M ได้ voucher 4 ชั่วโมง ต่อมามี voucher อีกใบสำหรับ MAC เดียวกันที่ช่วงเวลาซ้อนกัน (อาจเป็นคนเดิมหรือคนละคน) → log ของ M ในช่วงซ้อนกัน join ได้หลายแถว → แสดงเจ้าของมากกว่าหนึ่งราย ทั้งที่หนึ่งการเชื่อมต่อควรโยงกับ session ที่อนุญาตจริง

**ผลกระทบ:** การค้นย้อนหลัง/ใช้เป็นหลักฐานอาจระบุตัวผิดหรือซ้ำ และ pagination อาจนับแถวซ้ำ

**แก้:** เก็บตัวระบุ session/voucher ณ จุดที่ยืนยันสิทธิ์ และ join log กับช่วง `portal_session` ที่เปิดสิทธิ์จริง; ถ้าหลักฐานเดิมแยกไม่ได้ ให้แสดง “ระบุตัวไม่แน่นอน” แทนการเลือกชื่อบุคคลโดยอัตโนมัติ

### R06 — ลูกค้าเก่าถูกล้างตัวตนก่อน log ล่าสุดครบอายุ [สูง]

**หลักฐาน:** `app/admin/app.py:345-359` อัปเดต `customer.last_seen` ตอนออก voucher; การ login ใน `app/fas/app.py:201-246` ไม่อัปเดตค่านี้; `tools/purge_old_data.py:61-100` เลือกล้างตัวตนจาก `c.last_seen < cutoff` เมื่อไม่มี voucher active/ยังไม่หมดอายุ; log เองถูกลบด้วย cutoff จาก `ts` (`tools/purge_old_data.py:38-58`)

**ตัวอย่าง:** ออก voucher วัน D, ใช้งานจริงวันที่ D+1 ก่อน voucher หมดอายุ; เมื่อถึง D+180 ลูกค้าอาจถูกล้างเลขอ้างอิงแล้ว แต่ traffic log ของ D+1 ต้องอยู่ถึง D+181 ตามค่าเก็บ 180 วัน

**ผลกระทบ:** log ที่ยังอยู่สูญเสียเส้นทางผูกถึงผู้ใช้ แม้ข้อมูลจราจรไม่ได้ถูกลบก่อนเวลา

**แก้:** คำนวณวันล้าง PII จากกิจกรรมล่าสุดที่พิสูจน์ได้ รวม session/log ล่าสุดที่ยังต้องเก็บ และผูกนโยบายลบข้อมูลระบุตัวตนกับอายุหลักฐานจริง; ตรวจร่วมกับ `retention_hold_until()` ซึ่งปัจจุบันใช้ `portal_session.started_at` ไม่ใช่เวลาจบหรือเวลา log ล่าสุด (`app/common/customer.py:39-69`)

### R07 — FAS สร้าง authorization token จาก context ที่ผู้ใช้แก้ไขได้ [สูง; ผลการโจมตีต้องพิสูจน์]

**หลักฐาน:** GET ถอดรหัส FAS payload จาก openNDS (`app/fas/app.py:116-141`) แต่ POST กลับอ่าน `ctx_hid`, `ctx_gatewayaddress`, `ctx_authdir`, `ctx_clientmac` จาก hidden fields (`app/fas/app.py:84-95,143-160`); `build_auth_action_url()` ใช้ `hid` เหล่านี้สร้าง token และ URL (`app/fas/opennds_proto.py:172-199`)

**การป้องกันที่มี:** โค้ดเทียบ MAC กับ ARP ของ request IP และปฏิเสธเมื่อพบว่าไม่ตรง แต่หากหา ARP entry ไม่พบจะปล่อยผ่านตามโค้ด; ไม่มีการตรวจว่า context ใน POST คือ context ที่ server เคยถอดจาก GET เดียวกัน

**ผลกระทบ:** ฝั่ง client ควบคุมค่าที่ใช้สร้าง token และปลายทาง redirect ได้หลังจากมี voucher ถูกต้อง นี่เป็นช่องว่างของ trust boundary; จะใช้เปิดสิทธิ์ให้อุปกรณ์อื่นจริงได้หรือไม่ขึ้นกับข้อจำกัดของ openNDS และ topology ซึ่งรีวิวแบบ static ยืนยันไม่ได้

**แก้:** เก็บ context ที่ผ่านการถอดรหัสไว้ฝั่ง server ในอายุสั้น ใช้ nonce ผูกกับ request และ IP/MAC ที่เชื่อถือได้; POST อ้างเพียง nonce กับข้อมูล voucher และ validate gateway/authdir จากค่าตั้งต้นของระบบ

### R08 — บันทึก session ก่อน openNDS ยืนยันการเปิดสิทธิ์ [สูง]

**หลักฐาน:** `app/fas/app.py:201-257` insert `device` และ `portal_session` แล้วค่อย redirect browser ไปยัง openNDS; `tools/enforce_voucher_expiry.py:190-207` อธิบายกรณี session ผีและปิดภายหลังด้วย grace 180 วินาที

**ผลกระทบ:** ระหว่าง 0–180 วินาที ระบบอาจบอกว่าลูกค้าออนไลน์และใช้จำนวนอุปกรณ์ไปแล้ว ทั้งที่ openNDS ปฏิเสธหรือ browser ไม่ตาม redirect; หาก `ndsctl json` อ่านไม่ได้จะไม่ปิด session ผีในรอบนั้น (`tools/enforce_voucher_expiry.py:164-187,309-317`)

**แก้:** มีสถานะ pending ก่อน และยืนยันผลหลัง gateway อนุญาตจริง; อย่างน้อยต้องแยกตัวเลข pending กับ authenticated และคืนโควตาอุปกรณ์เมื่อไม่สำเร็จ

### R09 — รหัส voucher แบบ plaintext อยู่ใน Flask cookie ชั่วคราว [กลาง]

**หลักฐาน:** `app/admin/app.py:365-393` ใส่ `plain_pw` ใน `session['just_issued']` เพื่อ redirect แล้ว pop ใน GET; แอปใช้ Flask session ค่าเริ่มต้น (`app/admin/app.py:32-40`) ซึ่งเป็น signed client-side cookie ไม่ได้เข้ารหัส ขณะที่ `app/admin/templates/issue_result.html:6-8` และ `docs/privacy-policy-th.md:20` สื่อว่าเก็บรหัสเป็น hash เท่านั้น

**ผลกระทบ:** ผู้ที่ได้คุกกี้ของ browser พนักงานในช่วงนั้นสามารถอ่านรหัสจาก payload ได้โดยไม่ต้องรู้ `SECRET_KEY`; การ pop หลัง GET ลดช่วงเวลาแต่ไม่ได้เปลี่ยนข้อเท็จจริงว่า plaintext ถูกส่งเก็บฝั่ง client อย่างน้อยหนึ่งรอบ

**แก้:** ใช้ server-side one-time store ที่มีอายุสั้นและลบหลังเปิดหน้า หรือแสดงผลจาก POST โดยจัดการการกดซ้ำด้วย idempotency key; แก้ข้อความนโยบายให้แม่นยำจนกว่าจะเปลี่ยนวิธีเก็บ

### R10 — Audit log ล้มเหลวแล้วงานหลักยังสำเร็จ [กลาง]

**หลักฐาน:** `app/common/audit.py:31-42` กลืนทุก exception แล้วเขียนเพียง application log; เช่น `/customers/<id>/reveal` เรียก `audit.log()` ก่อนแสดงเลขบัตร (`app/admin/app.py:412-440`) และ `/issue` ทำงานสำเร็จแม้บันทึก audit ไม่ได้ (`app/admin/app.py:337-372`)

**ผลกระทบ:** คำรับรองว่า “ทุกครั้งที่เปิดเลขบัตรมี audit row” ไม่จริงในช่วง DB/audit table ล้มเหลว แม้หน้าเว็บอาจยังแสดงข้อมูลได้

**แก้:** สำหรับการเปิดเผยเลขเต็มและการส่งออกหลักฐาน ให้ fail closed เมื่อบันทึก audit ไม่ได้ หรือใช้กลไก durable queue ที่พิสูจน์ได้ว่าภายหลังจะเขียนครบ; งานที่ไม่อ่อนไหวอาจใช้ soft failure แต่ต้องแจ้งสถานะระบบ

### R11 — การลบ raw log ตามอายุทำให้ integrity checker แจ้งไฟล์หายตามปกติ [กลาง]

**หลักฐาน:** logrotate กำหนด `rotate ${LOG_RETENTION_DAYS}` และลบไฟล์เก่า (`install.sh:1782-1808`); `log_manifest` ไม่มีสถานะการหมดอายุ (`sql/001_schema.sql:129-140`); `verify_chain()` คาดว่าไฟล์ทุกชื่อใน manifest ยังอยู่ (`app/logger/integrity.py:151-185`)

**ผลกระทบ:** เมื่อเริ่มครบอายุไฟล์ archive ตัวตรวจจะแจ้ง `missing_file` และ maintenance อาจบันทึก `integrity_failed` ทุกคืน ทั้งที่ไฟล์ถูกลบโดยนโยบายปกติ ผู้ดูแลแยกการลบตามอายุกับการลบโดยมิชอบไม่ได้

**แก้:** บันทึกการลบ/หมดอายุอย่างตรวจสอบได้ พร้อม hash และเวลา; ให้ verifier ตรวจไฟล์ที่ยังอยู่และความต่อเนื่องของ manifest โดยรับรู้สถานะที่ลบตามกำหนด

### R12 — ค่า retention ต่ำกว่า 90 วันยังผ่านตัวติดตั้งแบบยืนยันได้ [กลาง]

**หลักฐาน:** `install.sh:1962-1965` เตือนแล้วเปิดให้ `confirm` ผ่านได้; `tools/purge_old_data.py:38-46` ปฏิเสธ cutoff ต่ำกว่า 90 วัน; logrotate ยังใช้ค่าที่รับมา (`install.sh:1782-1786`)

**ผลกระทบ:** ค่าเดียวกันทำให้ raw log หมุนเก็บตามค่าต่ำกว่า 90 วัน แต่ database purge ไม่ยอมทำงาน เกิดนโยบายเก็บสองที่ไม่ตรงกัน และคำเตือนอาจถูกผ่านโดยโหมดอัตโนมัติ ต้องตรวจ `confirm` ในการติดตั้งจริงหากจะประเมินผลแบบ `-y` อย่างแน่ชัด

**แก้:** ปฏิเสธค่าต่ำกว่า 90 ตั้งแต่ตรวจ CLI/wizard โดยไม่มีทางข้าม; ใช้ค่า retention ที่ validate แล้วร่วมกันทุกระบบ

### R13 — ข้อมูล DNS ของคำขอพร้อมกันชื่อเดียวกันจับคู่ผิดได้ [กลาง]

**หลักฐาน:** `app/logger/dns_collector.py:88-107` เก็บ pending query ใน dict โดยใช้ `qname` อย่างเดียว และ query ใหม่ชื่อเดียวกันเขียนทับตัวก่อน; answer ใช้ qname หา query ล่าสุด

**ตัวอย่าง:** เครื่อง A และ B ขอ `example.com` ใกล้กัน; pending ของ A ถูกแทนด้วย B ก่อนคำตอบของ A กลับมา → answer ของ A อาจถูกบันทึกเป็นของ B

**ผลกระทบ:** DNS Log บางแถวมี client IP/MAC ผิด และการค้นย้อนหลังอาจระบุผู้ใช้ผิด; dnsmasq text log อาจไม่มี query ID ให้จับแบบแน่นอน จึงควรระบุข้อจำกัดของแหล่งข้อมูลด้วย

**แก้:** ถ้ารูปแบบ log ให้ข้อมูลพอ ใช้ tuple ที่แยกคำขอได้; ถ้าไม่พอ ให้เก็บ raw query event แยกจาก response และระบุว่า answer correlation เป็นค่าประมาณ ไม่ใช้เป็นหลักฐานตัวตนเดี่ยว ๆ

## 4. ความเสี่ยงด้านสถาปัตยกรรมและข้อกล่าวอ้างที่ต้องระวัง

### S01 — รหัสลูกค้าส่งผ่าน HTTP หน้า portal [สูง; ความเสี่ยงขึ้นกับเครือข่าย]

`install.sh:1704-1721` เปิดหน้า FAS ผ่าน HTTP และ `app/fas/templates/login.html:9-27` ส่ง username/password ผ่าน POST หน้าเดียวกัน กลไก captive portal ที่ใช้ HTTP เพื่อให้ redirect ทำงานมีเหตุผลเชิงเทคนิค แต่ทำให้ credential ผ่านเครือข่ายโดยไม่มี TLS ที่ชั้นเว็บ หากมีผู้สังเกตทราฟฟิกบนทางเดินข้อมูลหรือ AP ปลอม รหัสชั่วคราวอาจถูกอ่านได้ ควรประเมินการใช้ HTTPS สำหรับหน้ากรอกรหัสหลัง redirect, วิธีแจกใบรับรองที่ใช้งานได้จริง และกำหนดอายุ/โควตา voucher ให้จำกัดความเสียหาย ในเล่มควรอธิบายข้อแลกเปลี่ยนนี้ตามจริง

### S02 — การป้องกัน bypass/isolation ไม่ใช่หน้าที่ Pi อย่างเดียว

`install.sh:1154-1168` มี nftables forward rules แต่ลูกค้าสองเครื่องใน L2 เดียวกันสามารถสื่อสารกันโดยไม่ผ่าน Pi; `docs/hardware-test-log.md:139-160` พิสูจน์แล้วว่า Guest Network ของ AP/เราเตอร์เป็นตัวบล็อกจริง และ `docs/hardware-test-log.md:100-126` แสดงว่าการตั้ง IP ให้อยู่ฝั่ง uplink ข้าม portal ได้เมื่อเราเตอร์ไม่มี ACL ดังนั้นการติดตั้งจริงต้องกำหนดอุปกรณ์/ค่าตั้งขั้นต่ำของเราเตอร์และ AP อย่างชัดเจน อีกทั้งต้องปิด IPv6 หรือออกแบบการบังคับ IPv6 ให้ครบ (`docs/hardware-test-log.md:389-396`)

### S03 — Checksum ไม่เท่ากับการยืนยันตัวบุคคล

`app/common/crypto.py:53-68` ตรวจความถูกต้องของเลข 13 หลักตามสูตร; `app/admin/templates/issue.html:44-46` ให้พนักงานกดยืนยันว่าแจ้งและได้ความยินยอมแล้ว ไม่มีเส้นทางโค้ดตรวจว่าบัตรเป็นของผู้มารับ voucher จริง ข้อความในเล่มควรใช้ “ลงทะเบียนโดยอ้างอิงเลขบัตรและตรวจ checksum” และอธิบายขั้นตอนตรวจบัตรของพนักงานเป็นมาตรการนอกระบบหากมีจริง อย่าอ้างว่าโปรแกรมพิสูจน์เจ้าของบัตรได้

### S04 — ความสมบูรณ์ของ log ยังมีขอบเขต

Connection collector ฟัง `conntrack -E ... DESTROY` (`app/logger/conn_collector.py:239-256`) ซึ่งเป็นเหตุการณ์เมื่อรายการจบ มิใช่ทุก packet และเคยมีหลักฐาน ENOBUFS ในแล็บตาม `docs/hardware-test-log.md:308-345` การทดสอบซ้ำ 500/500 ดีและควรรายงาน แต่ไม่ใช่หลักประกันว่าจะไม่หายเมื่อโหลดสูงหรือ DB/collector มีปัญหา DNS log ก็ไม่เห็น DoH/DoT ตามข้อจำกัดที่โครงงานบันทึกเอง (`PROJECT_PLAN.md:643-648`)

### S05 — การสำรองข้อมูลยังอยู่บนเครื่องเดียวเป็นค่าปริยาย

`tools/backup_db.py:124-151` รองรับ offsite แต่ถ้าไม่ตั้ง `OFFSITE_BACKUP_DIR` จะข้าม `docs/hardware-test-log.md:397` ระบุว่ายังไม่ได้ตั้งค่าสำรองออกนอกเครื่อง ความเสียหายของ microSD ทั้งใบจึงกระทบทั้ง DB และ backup ในเครื่อง ควรมีนโยบายสำรองออกนอก Pi และซ้อมกู้คืนก่อนใช้งานจริง

## 6. ประเด็นกฎหมายและข้อมูลส่วนบุคคลที่ต้องตรวจโดยผู้เชี่ยวชาญ

แหล่งหลักที่ตรวจประกอบรายงานนี้คือหน้ารวม [กฎหมายการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ของ ETDA](https://www.etda.or.th/th/Useful-Resource/law/computer-crimes.aspx) และ [ประกาศหลักเกณฑ์การเก็บรักษาข้อมูลจราจรทางคอมพิวเตอร์ของผู้ให้บริการ พ.ศ. 2564](https://www.etda.or.th/getattachment/f1456b62-e9ee-4d05-8493-aceef24c718f/%E0%B8%9B%E0%B8%A3%E0%B8%B0%E0%B8%81%E0%B8%B2%E0%B8%A8%E0%B8%81%E0%B8%A3%E0%B8%B0%E0%B8%97%E0%B8%A3%E0%B8%A7%E0%B8%87%E0%B8%94%E0%B8%88%E0%B8%97%E0%B8%A5%E0%B9%80%E0%B8%9E%E0%B8%AD%E0%B9%80%E0%B8%A8%E0%B8%A3%E0%B8%A9%E0%B8%90%E0%B8%81%E0%B8%88%E0%B9%81%E0%B8%A5%E0%B8%B0%E0%B8%AA%E0%B8%87%E0%B8%84%E0%B8%A1-%E0%B9%80%E0%B8%A3%E0%B8%AD%E0%B8%87-%E0%B8%AB%E0%B8%A5%E0%B8%81%E0%B9%80%E0%B8%81%E0%B8%93%E0%B8%91%E0%B8%81%E0%B8%B2%E0%B8%A3.aspx) ซึ่งระบุการเก็บอย่างน้อย 90 วันและรายละเอียดข้อมูลที่ต้องพิจารณาตามประเภทผู้ให้บริการ

การตั้ง `LOG_RETENTION_DAYS=180` เป็นเพียงส่วนหนึ่งของการประเมิน ต้องตรวจความครบถ้วน ความถูกต้องของเวลา การเชื่อมข้อมูลถึงผู้ใช้ การเข้าถึง/ส่งมอบหลักฐาน และกรณีข้อมูลสูญหายด้วย การใช้เลขบัตรประชาชนเป็นวิธีอ้างอิงตัวตนและระยะเก็บเลขบัตรควรให้ผู้เชี่ยวชาญตรวจฐานทางกฎหมาย ความจำเป็น และประกาศความเป็นส่วนตัวก่อนนำไปใช้จริงกับลูกค้า รายงานนี้ไม่ตัดสินว่าระบบ “ผิด” หรือ “สอดคล้อง” กฎหมายแล้ว

## 7. แผนแก้และเกณฑ์รับงานที่แนะนำ

### ก่อนส่งหรือสาธิต

1. แก้ R01–R03 แล้วเพิ่มการตรวจว่า DNS/Connection collector ยังเก็บแถวใหม่จริง ไม่ใช่ดูเพียง service active
2. แก้ R04–R06 เพื่อไม่ให้หลักฐานขาดหรือโยงผิดคน; จัดการข้อมูลเก่าที่ mapping ไม่แน่นอนโดยไม่อ้างตัวบุคคลเกินหลักฐาน
3. แก้ R07–R08 เพื่อผูก context กับคำขอที่ถอดจาก gateway และแยกสถานะ pending/authenticated
4. ย้าย plaintext voucher ออกจาก Flask cookie (R09), กำหนดพฤติกรรมเมื่อ audit ล้มเหลว (R10), และทำให้ verifier เข้าใจการลบตามอายุ (R11)
5. ปิดทางตั้ง retention ต่ำกว่า 90 วัน (R12) และอัปเดตเอกสารสถานะการทดสอบให้ตรงกับหลักฐานล่าสุด

### กรณีทดสอบที่ควรเพิ่มภายหลังเมื่อได้รับอนุญาตให้รัน

|---|---|

| MariaDB หยุดชั่วคราวระหว่างมี DNS/Connection events | collector retry หรือบันทึก `log_gap` พร้อมจำนวน/ช่วงเวลาที่หาย; ไม่มีการล้าง buffer เงียบ ๆ |
| DNS collector หรือ conn collector จบด้วย exception | service ออก nonzero, systemd restart และหน้า status/alert แสดงความผิดปกติ |
| ไม่มี ARP entry ตอน conntrack DESTROY | raw event ยังถูกเก็บหรือมีตัวนับ/alert ว่าจับคู่ไม่ได้ |
| MAC เดียวมี voucher ช่วงเวลาซ้อนกัน | log หนึ่งแถวไม่ถูกระบุตัวเป็นสองคนโดยไม่มีหลักฐาน session |
| ออก voucher วัน D แต่ใช้จริงวัน D+1 | PII ยังอยู่จน log ของ D+1 พ้นกำหนดเก็บ |
| แก้ hidden fields ใน FAS POST | server ปฏิเสธ context ที่ไม่ใช่ชุดจาก openNDS/คำขอ GET เดิม |
| gateway ปฏิเสธหรือ browser ไม่ตาม redirect | ไม่มี session ที่รายงานว่า authenticated และโควตาอุปกรณ์ถูกคืนตามนโยบาย |
| raw log ครบอายุแล้วถูกลบตามนโยบาย | verifier ไม่แจ้ง `missing_file` เท็จ แต่ยังตรวจการลบผิดปกติได้ |
| ทดสอบ ARP spoof, IPv6 เปิด, และ 20 client | บันทึกผลพร้อมผังเครือข่าย/ค่าตั้ง AP และระบุขอบเขตที่ทดสอบจริง |

## 8. ข้อเสนอสำหรับการพัฒนาต่อ

- ใช้ server-side session หรือ session identifier ที่อ้างอิง voucher และ gateway แทนการอาศัย MAC เป็นตัวระบุตัวตนเพียงอย่างเดียว
- เพิ่ม CSRF protection สำหรับ Admin Panel และตรวจสิทธิ์พนักงานจากฐานข้อมูลเมื่อทำรายการอ่อนไหว แทนการเชื่อ role ใน cookie ตลอดอายุ session (`app/admin/app.py:98-113,254-260`)
- จำกัดช่วงเวลาค้นหา log และ page offset สูงสุด พร้อมดัชนี/รูปแบบค้นหาที่รองรับข้อมูล 90–180 วันจริง (`app/admin/app.py:538-611`); ตรวจประสิทธิภาพเมื่อข้อมูลโต
- ออกแบบเส้นทางเก็บ log ให้มีตัวนับ “รับมา/เขียนได้/ทิ้ง/จับคู่ไม่ได้” แยก Connection และ DNS และแสดงใน Admin status
- ซ้อมกู้คืนจาก backup นอก Pi โดยตรวจ schema, event scheduler, key material และความสามารถถอดรหัสข้อมูลเดิม

## 9. ขอบเขตของรายงานนี้

ไม่ได้ตรวจ dependency versions กับฐานช่องโหว่ปัจจุบัน ไม่ประเมิน penetration test และไม่ยืนยันค่า config ที่ติดตั้งอยู่บนเครื่อง Pi จริง สถานะทดสอบในรายงานอ้างจากเอกสารที่มี ไม่ใช่ผลทดสอบใหม่ การแก้โค้ด/ตั้งค่าและการทดสอบรับงานทั้งหมดเป็นขั้นตอนถัดไป
