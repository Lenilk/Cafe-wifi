# แผนทดสอบโหลด Raspberry Pi gateway (T14)

เอกสารนี้ใช้หาจำนวน **อุปกรณ์ลูกค้าที่ใช้งานพร้อมกัน** ที่ Raspberry Pi gateway รองรับได้ภายใต้รูปแบบทราฟฟิกที่กำหนด พร้อมตรวจว่าระบบเก็บหลักฐานจราจรครบถ้วน อ้างอิง [แผนทดสอบ](test-plan.md) และ [ผลทดสอบฮาร์ดแวร์](hardware-test-log.md)

**สถานะก่อนเริ่ม:** T14 ยังไม่ได้ทดสอบ 20 เครื่องพร้อมกัน ผลเดิมยืนยันสูงสุด 3 เครื่อง ความเร็ว 319–324 Mbit/s ที่เคยวัดได้เป็นผลทดสอบความเร็วด้วยเครื่องลูกค้า ไม่ใช่จำนวนคนหรือเพดานของ Pi และการ login จริงเคยใช้เวลาประมาณ 3.9 วินาที จึงต้องรายงานเวลานี้แยกจากความหน่วงหน้า FAS

## 1. ขอบเขตและชุดทดสอบ

| ชุด | สิ่งที่พิสูจน์ | วิธี | ข้อจำกัดของผล |
|---|---|---|---|
| A: อุปกรณ์จริง | เส้นทาง Wi-Fi → DHCP → captive portal → login → อินเทอร์เน็ต และประสบการณ์ผู้ใช้ | มือถือ/โน้ตบุ๊ก 2–3 เครื่องหรือเท่าที่มี | ยืนยันได้เฉพาะจำนวนเครื่องจริงที่ใช้ |
| B: ลูกค้าจำลอง | ความจุของ Pi, openNDS, NAT, DNS, ฐานข้อมูล และ logger เมื่อมี MAC/IP หลายราย | เครื่อง Linux แยก network namespace + macvlan หนึ่งคู่ต่อราย ต่อผ่านพอร์ต LAN ฝั่งลูกค้า | ไม่วัดความจุคลื่นวิทยุและ AP; ต้องระบุวิธี auth ที่ใช้ |
| C: FAS HTTP | ความหน่วงของเว็บพอร์ทัลเมื่อมีคำขอจำนวนมาก | เครื่องสร้างโหลดส่ง GET `/policy` ที่ 50 requests/วินาที | 50 requests/วินาทีไม่ใช่ลูกค้า 50 คน และไม่ได้พิสูจน์การ login |

หากต้องการอ้างว่า **20 เครื่อง login ครบวงจรจริงพร้อมกัน** ต้องให้ลูกค้าทั้ง 20 รายผ่าน redirect ของ openNDS, ฟอร์ม FAS, auth URL และปรากฏเป็น `Authenticated` ใน `ndsctl json` พร้อมมี `portal_session` ที่ยืนยันแล้ว การสั่งเปิดสิทธิ์ด้วย `ndsctl auth` ใช้ทดสอบการส่งต่อข้อมูลหลัง auth ได้ แต่ **ไม่นับ** เป็นผลทดสอบ FAS/login ครบวงจร เพราะข้ามการตรวจ voucher และการบันทึก session ของแอป

## 2. ผังแล็บและสิ่งที่ต้องเตรียม

```text
เครื่องสร้างโหลด Linux (สาย LAN; หลาย namespace/MAC) ─┐
                                                      ├─ LAN/SSID ลูกค้า ─ Pi 4B gateway ─ เราเตอร์ ─ อินเทอร์เน็ต/เครื่องรับโหลด
มือถือหรือโน้ตบุ๊กจริง (Wi-Fi) ────────────────────────┘
```

- Pi ใช้ระบบที่ติดตั้งจริงตาม `install.sh`: client gateway `10.10.0.1/24`, DHCP pool ค่าเริ่มต้น `10.10.0.100–250`, FAS `:8080`, openNDS `:2050`; **อ่านค่าจริงบนเครื่องก่อนทดสอบ** หากปรับค่าตอนติดตั้ง คำสั่งตัวอย่างด้านล่างต้องเปลี่ยนตาม
- เครื่อง Linux สำหรับสร้างโหลดต้องอยู่อีกเครื่องหนึ่ง ไม่สร้าง namespace บน Pi เพราะจะทำให้ Pi รับภาระของตัวสร้างโหลดเอง ใช้พอร์ตสวิตช์ที่อยู่ L2 เดียวกับลูกค้า และตรวจว่าพอร์ตยอมรับหลาย MAC/ไม่มี port security ขวาง
- เครื่องรับโหลดควรเป็นเซิร์ฟเวอร์ที่ควบคุมได้และอยู่ **หลังเส้นทางออกจาก Pi** เช่น VPS ที่มี IPv4 สาธารณะ และรัน `iperf3 -s`/HTTP server การยิงไปยังบริการที่รันบน Pi เองไม่วัด forwarding/NAT; การยิงไปยัง IP เอกชนฝั่ง uplink ถูกกฎ firewall ของโครงการบล็อกอยู่ อย่าแก้ firewall เพื่อให้ผลทดสอบผ่านโดยไม่บันทึกการเปลี่ยนแปลง
- เตรียม voucher ทดสอบแยกหนึ่งใบต่อ MAC (หรือกำหนด `max_devices` ให้พอ), อายุและโควตาสูงพอตลอดการทดสอบ เก็บรหัสผ่านไว้ที่เครื่องสร้างโหลดเท่านั้น ไม่ใส่รหัสหรือข้อมูลบัตรจริงลงรายงาน ใช้ข้อมูลบุคคลทดสอบตามขั้นตอนของระบบ
- บันทึก Pi รุ่น, RAM, ระบบปฏิบัติการ, kernel, สื่อเก็บข้อมูล, รุ่น AP/เราเตอร์, ความเร็วพอร์ต, ความเร็วอินเทอร์เน็ต, วันเวลา และ commit ของโค้ดในรายงานทุกครั้ง

ก่อนยิงโหลด ตรวจ baseline จาก Pi:

```bash
ip -br addr
sudo systemctl --failed
sudo ndsctl status
sudo ndsctl json
cat /var/log/cafe-wifi/collector-conn.json
cat /var/log/cafe-wifi/collector-dns.json
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
```

ถ้าบริการไม่ครบ, DHCP ไม่ได้แจก IP จาก Pi, `ndsctl` ใช้ไม่ได้ หรือ collector ไม่มี heartbeat/มี error อยู่แล้ว ให้แก้สภาพแล็บก่อนเริ่มจับเวลา เพื่อไม่ปะปนความเสียหายเดิมกับผลทดสอบ

## 3. สร้างลูกค้าจำลองและยืนยันเส้นทาง

บนเครื่อง Linux **ที่ไม่ใช่ Pi** ใช้ `iproute2`, DHCP client, `curl`, `dig`, `iperf3` และ `vegeta` (สำหรับชุด C) ตัวอย่างหนึ่งรายต่อไปนี้ให้เปลี่ยน `enp3s0` เป็น NIC จริงของเครื่องสร้างโหลด:

```bash
sudo ip netns add cw01
sudo ip link add link enp3s0 name cw01 type macvlan mode bridge
sudo ip link set cw01 netns cw01
sudo ip -n cw01 link set lo up
sudo ip -n cw01 link set cw01 address 02:ca:fe:00:00:01
sudo ip -n cw01 link set cw01 up
sudo ip netns exec cw01 dhclient -1 -v -pf /tmp/dhclient-cw01.pid -lf /tmp/dhclient-cw01.leases cw01
sudo mkdir -p /etc/netns/cw01
printf 'nameserver 10.10.0.1\n' | sudo tee /etc/netns/cw01/resolv.conf
sudo ip -n cw01 -br addr
sudo ip -n cw01 route
sudo ip netns exec cw01 dig @10.10.0.1 neverssl.com
sudo ip netns exec cw01 curl --noproxy '*' -i --max-time 10 http://neverssl.com/
```

ต้องเห็น IP `10.10.0.x` จาก DHCP ของ Pi, default gateway `10.10.0.1` และก่อน login ได้ redirect ของ openNDS ไปยังหน้า FAS แทนหน้าเว็บปลายทาง ใช้ MAC แบบ locally administered ที่ไม่ซ้ำกัน (`02:...`) และ namespace ใหม่ต่อราย เปลี่ยนชื่อ namespace, MAC, PID/lease file และ `/etc/netns/<ชื่อ>/resolv.conf` ให้ตรงกันทุกครั้งเมื่อเพิ่มรายใหม่ ถ้า DHCP client ในเครื่องไม่ใช่ `dhclient` ให้ใช้ตัวที่ติดตั้งอยู่โดยคงเงื่อนไขว่าต้องขอ lease จริงจาก Pi; ห้ามกำหนด IP เองแล้วนับเป็นผล DHCP หลังทดสอบให้ปล่อย lease, หยุดโปรเซสใน namespace แล้วลบเฉพาะ namespace/ไฟล์ที่สร้างสำหรับรอบนั้น

สำหรับการทดสอบผ่าน FAS ครบวงจร ตัวขับลูกค้าแต่ละ namespace ต้องทำตามลำดับนี้ โดยเก็บ cookie/redirect แยกกันและ **ไม่อ่าน FAS_KEY จาก Pi**:

1. ขอเว็บ HTTP ภายนอกและตาม redirect ไป `/login?fas=...&iv=...` ที่ openNDS สร้างจริง
2. อ่านค่า `nonce` จากฟอร์ม แล้ว POST `username`, `password`, `nonce` ของ voucher สำหรับ MAC นั้น
3. ตาม 302 ไปที่ auth URL ของ openNDS จาก namespace **เดียวกัน**; ห้ามเรียก auth URL จากเครื่องแม่หรือ Pi
4. ตรวจ `ndsctl json` ว่า MAC/IP ตรงและสถานะ `Authenticated` แล้วค่อยเริ่มโหลด ตรวจ `portal_session.state='authenticated'` หลังตัว reconcile ทำงาน

ในรีโปนี้ยังไม่มีตัวขับ HTTP สำหรับ 20 namespace ที่ทำครบ 4 ขั้นตอน จึงต้องเตรียมตัวขับและทดสอบกับ 1 namespace ก่อนขยายจำนวน ระหว่างที่ยังไม่มี ให้ใช้ชุด A ยืนยัน login จริง และใช้ชุด B วัด forwarding ของลูกค้าที่เปิดสิทธิ์ผ่าน `ndsctl auth` โดยติดป้ายผลว่า **gateway forwarding เท่านั้น** ห้ามนำไปปิด T14 แบบครบวงจร ความล้มเหลวจาก voucher หมดสิทธิ์, device limit หรือ rate limit (`5` ครั้งผิดพลาดต่อ MAC ภายใน `10` นาที) ต้องแยกออกจากความล้มเหลวเพราะโหลด

## 4. ขั้นตอนรันทดสอบ

1. **Baseline:** ทดลอง 1–3 เครื่องจริงให้ได้ IP, เด้ง portal, login, เปิดเว็บและมี DNS/connection log จากนั้นวัดความเร็วเครื่องสร้างโหลด↔เครื่องรับโหลดโดยไม่ผ่าน Pi เพื่อยืนยันว่าตัวสร้างโหลดและปลายทางมีความจุสูงกว่าระดับที่จะวัด
2. **Login burst:** เพิ่มลูกค้า 5, 10, 20, 30, 40 รายตามลำดับ ให้รายใหม่เริ่ม login ภายใน 60 วินาทีของรอบเดียวกัน จับเวลาเริ่มจน `Authenticated` รายสุดท้าย แยกจำนวนสำเร็จ/ล้มเหลวและสาเหตุ; ถ้าใช้ `ndsctl auth` ให้รายงานเป็นรอบเปิดสิทธิ์ gateway ไม่ใช่รอบ FAS
3. **Steady load:** คงแต่ละระดับไว้ 15 นาที ให้ทุกราย query DNS ทุก 10 วินาที และดาวน์โหลดไฟล์ HTTP จากเครื่องรับโหลดประมาณ 25 KB ทุกวินาที (ประมาณ 0.2 Mbit/s ต่อราย หรือ 8 Mbit/s ที่ 40 ราย) ใช้ภาระต่อรายเท่าเดิมทุกระดับ กระจายเวลาเริ่มเพื่อไม่สร้าง burst โดยบังเอิญ บันทึกจำนวนคำขอและปริมาณข้อมูลที่สำเร็จจริง ตรวจอุปกรณ์ Wi-Fi จริงอย่างน้อย 1 เครื่องระหว่างรอบ หาก uplink ที่ใช้จริงต่ำกว่าโหลดรวม ให้ลดอัตรา **ก่อน** เริ่มทุกระดับและบันทึกค่าใหม่ ห้ามลดเฉพาะระดับที่เริ่มไม่ผ่าน
4. **Connection burst:** ที่ระดับ 20 ราย เปิดและปิด connection สั้นจำนวนเท่ากันจากแต่ละรายเป็นรอบแยก จดจำนวน connection ที่เครื่องสร้างโหลดทำสำเร็จจริง แล้วเทียบกับ `conn_log` หลัง connection ปิดและรอให้ collector เขียนครบ (TCP บางรายการยังอยู่ใน conntrack ระยะหนึ่ง); หยุดรอบทันทีหากพบ `ENOBUFS` หรือ `log_gap` รอบนี้สำคัญเพราะระบบเคยสูญเสีย log เมื่อเหตุการณ์ conntrack จบพร้อมกัน
5. **FAS HTTP:** ยิง GET `/policy` ที่ 50 requests/วินาทีเป็นเวลา 5 นาทีเมื่อ gateway ว่างเพื่อเก็บ baseline แล้วรันซ้ำ **ระหว่างที่ลูกค้า 20 รายส่ง steady load อยู่** วัด p50/p95/p99 และ error rate ทั้งสองรอบ; ไม่ใช้ POST `/login` ซ้ำด้วย voucher เดิม เพราะ nonce ใช้ครั้งเดียวและจะทำให้ผลปะปนกับการป้องกันการลองรหัส หากเครื่องเดียวสร้างทั้งโหลดลูกค้าและ FAS ให้เฝ้า CPU ของเครื่องนั้นด้วย
6. **ยืนยันขีดจำกัด:** ระดับสูงสุดที่ผ่านครบทุกข้อให้ทดสอบซ้ำ 30 นาที โดยเปิด FAS HTTP 50 requests/วินาทีอย่างน้อย 5 นาทีในรอบนั้นด้วย หาก 40 รายยังผ่าน ให้เพิ่มครั้งละ 10 จนเจอระดับแรกที่ไม่ผ่านหรือชนเพดานของแล็บ/ช่วง DHCP แล้วรายงานเหตุที่หยุด ไม่คาดเดาเพดานที่สูงกว่า

ทดสอบความเร็วส่งต่อข้อมูลแยกจาก steady load ด้วย `iperf3` จาก namespace เช่น `sudo ip netns exec cw01 iperf3 -c <public-ip-of-owned-server> -t 60` บันทึกผลทั้งฝั่ง client และ server หากต้องการให้หลาย namespace ยิง `iperf3` พร้อมกัน ให้เตรียมเซิร์ฟเวอร์หลายพอร์ต/หลายอินสแตนซ์หรือยืนยันก่อนว่าเวอร์ชันเซิร์ฟเวอร์รับหลาย client พร้อมกันได้ การทดสอบ steady load ใช้ HTTP เพื่อไม่ให้ข้อจำกัดนี้กลายเป็นคอขวดโดยไม่รู้ตัว

ตัวอย่างชุด C จาก namespace ที่ได้ IP ลูกค้าแล้ว (ติดตั้ง `vegeta` บนเครื่องสร้างโหลดก่อน):

```bash
printf 'GET http://10.10.0.1:8080/policy\n' | sudo ip netns exec cw01 vegeta attack -duration=5m -rate=50 | vegeta report
```

ตัวอย่าง DNS marker เพื่อเทียบรายการที่ส่งกับฐานข้อมูล: ให้แต่ละรายถามชื่อที่ไม่ซ้ำ เช่น `load-cw01-r01.example.test` ผ่าน `dig @10.10.0.1` แล้วค้น `dns_log` ในช่วงเวลาเดียวกันโดย `qname`/`client_ip` การตอบ NXDOMAIN ไม่ถือว่าล้มเหลวของการเก็บ query; ตรวจว่า query ปรากฏครบตามจำนวนที่ส่ง ส่วน `conn_log` ให้เทียบเฉพาะ connection ที่ปิดแล้วกับรายการจากเครื่องปลายทาง ไม่ใช้เพียงจำนวนแถวรวมของตาราง

## 5. สิ่งที่วัดและเกณฑ์ผ่าน

เก็บ snapshot ก่อนและหลังทุกรอบ และดูตัวเลขระหว่างรอบทุก 5–10 วินาที:

| ตัวชี้วัด | แหล่งข้อมูล | เกณฑ์ผ่าน T14 |
|---|---|---|
| จำนวนลูกค้าที่ใช้ได้จริง | ผลจากแต่ละ namespace + `ndsctl json`; ถ้าทดสอบ FAS เต็มให้เทียบ `portal_session` | เท่าจำนวนที่ตั้งไว้และใช้งานได้ตลอดรอบ |
| เวลา FAS HTTP | ตัวสร้างโหลด; รายงาน p50/p95/p99 และ error | p95 ของ GET `/policy` ต่ำกว่า 2 วินาทีและไม่มี HTTP 5xx |
| Login | จับเวลาจาก redirect แรกถึง `Authenticated` | รายงานแยก ไม่ใช้เกณฑ์ 2 วินาทีของ FAS; ทุกคำขอที่ถูกต้องต้องสำเร็จ |
| DNS/connection log | `collector-*.json`, `audit_log`, `journalctl -u cafe-logger` และตัวนับเหตุการณ์ฝั่งสร้างโหลด | ไม่มี `dropped` เพิ่ม, `log_gap` ใหม่หรือ `ENOBUFS`; เหตุการณ์ทดสอบที่ตรวจแบบรายรายการต้องบันทึกครบ |
| เสถียรภาพและทรัพยากร | `systemctl`, CPU/RAM, `vcgencmd get_throttled`, อุณหภูมิ, conntrack count/max, throughput | ไม่มีบริการล่มหรือ thermal throttling; ตัวสร้างโหลด/ลิงก์ปลายทางไม่เต็มก่อน Pi |

ตัวอย่างคำสั่งดูระหว่างรอบบน Pi:

```bash
sudo ndsctl json
```

ตรวจ `audit_log` ของช่วงรอบด้วย `SELECT ts, action, detail FROM audit_log WHERE ts >= '<เวลาเริ่ม>' AND ts < '<เวลาจบ>' AND action='log_gap' ORDER BY ts;` ให้ใช้เวลาจริงที่บันทึกไว้ ส่วน `collector-*.json` เป็น counter ต่ออายุโปรเซส: ถ้า collector restart ระหว่างรอบ ตัวเลขอาจเริ่มใหม่ ต้องตรวจ journal และนับรอบนั้นว่าไม่ผ่าน อย่าเอา counter หลัง restart ลบกับก่อน restart แล้วสรุปว่าไม่ drop

**จำนวนที่รองรับที่รายงาน** = จำนวนสูงสุดที่ผ่านทั้งรอบ 15 นาทีและรอบยืนยัน 30 นาที ภายใต้ workload ที่ระบุ สำหรับการปิด T14 ที่ 20 ราย ต้องผ่าน **ขณะ** FAS รับ 50 requests/วินาทีด้วย ถ้าเครื่องสร้างโหลด, VPS, อินเทอร์เน็ต, DHCP pool หรือ AP เต็มก่อน ให้รายงานว่า “วัดได้อย่างน้อย N ราย; ยังไม่พบเพดานของ Pi” หรือ “ติดคอขวดที่ X” แทนการอ้างว่า Pi รองรับได้สูงสุด N ราย
